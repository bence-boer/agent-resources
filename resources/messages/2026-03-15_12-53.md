Your task is to distill the skill "svelte-architect" into two separarate, *minimally* overlapping skills. One of these skills should be an actual architect (you can name it "svelte-architect-new" to avoid name collision) whose responsibility will solely be to be concerned about architecture. It should be analytical, critical, thinking about the overall structure of the application, global (or domain-specific) abstractions, a comprehensive overview of the application and decisions. It should NOT be concerned about the specific implementation details. It should also focus on feature completeness, user experience, and long term extensibility and maintainability for choosing the right technological and architectural solutions (inside the svelte app and ecosystem). It should be prepared for architecting an application from scratch (setting up linting, initial folder/component/state handling architecture, global primitive components, libraries to be used, etc, etc) as well as reviewing and extending an existing application, rethinking existing patterns for optimal integrations. It should also contain some amount of concrete architectural best practices. You can check the already existent skills: "agent-instructor", "meta-engineer", and the instructions/copilot-instructions.md as references, just as food for thought, but not as source of content. The other skill created out of the current svelte skill should be more pragmatic, still involve thinking, but mainly focus on implementation and file-level strategies. You can name it "svelte-engineer". It can contain more hard rules, but it should still have the ability to think, to be able to decide how to split files if they get too large (based on separation of concerns, etc) and create minimal abstractions. It can also contain details about for example how a component's prompts, slots and events should be structured, how they should be exposed, how they should be named, etc, how pages should be structured (minimal "orchestrator" around dumb and smart components), how a functionality should be broken down to separate files/components with clear data/functionality ownership and role boundaries). It should be a versatile engineer prepared to implement any architecture or task with maximal coverage and precision. Use the "skill-creator" skill to create both. If you're unsure about the best pattern for something in either skill implementation (but really only if you're unsure) dispatch a subagent (utilize "agent-instructor" skill) to find the pattern you are looking for in ../ralph-agent-workspace.
