You will be an agent orchestrator and your task is going to be to coordinate agents to create an in-depth architecture and implementation review of the app's svelte frontend, then act upon it. Please load the entirety of the svelte-architect and the svelte-engineer skills, split the topics inside them into 10-20 different categories and dispatch as many explorer agents as you see fit to see and get a comprehensive view about what parts of the skills are applicable to the frontend codebase in ./web. The app is self hosted with static site rendering (not svelte-kit) so items related to other types of hosting or building in that regard are not applicable. After you see what parts of the skills are applicable to the codebase (which should be most), dispatch rigorous verifier agents (one per topic, which means 10-20 agents in total) to see whether the right methodologies are applied regarding their respective topics across EVERYWHERE in the app. I mean it. Literally everywhere. They should save their findings about compliance and non-compliance into some temporary markdown files BECAUSE once all of them are finished, your task will be to dispatch another agent which looks through all of the reports and compiles a final report by removing duplicate findings and grouping, organizing and structuring information in a logical manner (sometimes large file tool calls fail, so this agent and in general all agents should execute large write operations in at max 200-300 lines long batches). Once this master review file is done, your task will be to dispatch another agent to look through the master review file, and split mitigation tasks between as many agents as necessary for complete and 100% coverage work. Something you and this agent should both know is that we have infinite compute resources, so the only goal should be to complete the task in the best possible way possible, using as many agents as needed. If you come up with some better splitting up of any task or subtask of the process that requires more subagents but yields more reliable results, feel free to do it that way. After the latest (planning) agent has come up with the optimal split and implementation plan, it should save it to a file, and you should look at this file, and dispatch all edit subagents SEQUENTIALLY (because unfortunately agents cannot communicate and they tend to overwrite each other's work when running in parallel). After EACH sequential implementation agent you should run a verifier agent to check if the implementation agent has done its job well. The verifier agents can collect their findings as separate files in a shared directory, and at the end, after all the implementation and verifier agents have run, you should dispatch one last subagent that takes all the findings of the verifier agents and fixes any leftovers based on that. After this is done, clean up the temporary planning and audit files, commit and push the code changes (when committing do NOT use --no-verify), and E2E test whether the application works correctly everywhere on a running instance. Iterate on the fixes until everything works. Use subagents for everything. Use the agent-instructor skill. The precommit hook contains unit tests, the gh CI pipeline contains E2E tests that run on the test environment (test.clanqr.dev). You are not done until the CI is green. Use subagents for that too. Update unit and E2E tests where needed, but do not decrease coverage. You've done your job right if by the end you've run 70+ agents.
