# Domain — User value

## Use when

The change affects what people can do, feel, trust, or notice.

## Route next

- [workflow-fit.md](workflow-fit.md) — to place that value inside the surrounding journey
- [error-handling.md](error-handling.md) — to preserve trust when the ideal path breaks
- [../finish/self-review.md](../finish/self-review.md) — to ask whether the result actually feels worth it

## Questions

- What user, buyer, or operator outcome justifies this work? (e.g., less waiting, fewer mistakes, more trust, new capability)
- What detail would make the result feel thoughtful instead of transactional? (e.g., clear wording, better defaults, fewer clicks, contextual help)
- What would disappoint the user even if the ticket is technically complete? (e.g., missing status, awkward edge case, confusing state, jarring transition)
- What tradeoff are you making on the user's behalf, and is it the right one? (e.g., speed vs clarity, power vs safety, density vs simplicity)
- Does this solve the root problem, or is it patching a symptom? (e.g., fixing the data model vs adding another conditional, addressing the cause vs hiding the effect)
