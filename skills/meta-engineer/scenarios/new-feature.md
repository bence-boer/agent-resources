# Scenario — New feature

## Use when

The task adds a capability rather than only correcting or reorganizing existing behavior.

## Route next

- [../domains/user-value.md](../domains/user-value.md) — to define why the feature deserves to exist
- [../domains/workflow-fit.md](../domains/workflow-fit.md) — to make the feature feel native to existing flows
- [../domains/error-handling.md](../domains/error-handling.md) — to design failure and recovery instead of bolting them on later
- [../domains/maintainability.md](../domains/maintainability.md) — to keep the new surface easy to extend
- [../domains/extensibility.md](../domains/extensibility.md) — to prepare for the next variant without over-engineering

## Questions

- What new ability should users or operators gain, and why now? (e.g., faster setup, fewer manual steps, better visibility)
- How should this fit the existing product instead of feeling bolted on? (e.g., same navigation, same language, same mental model)
- What downstream behaviors, permissions, data, or support burden does this feature create? (e.g., new state, more docs, more alerts, edge cases)
- What would make this feature feel complete on first release? (e.g., clear empty state, safe defaults, obvious recovery, polished flow)
