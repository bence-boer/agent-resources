## Validating Information Architecture

Before committing to a navigation structure, validate with users — not assumptions.

- **Open Card Sorting:** Give users content items on cards and ask them to group and name categories. Reveals how users naturally categorize information.
- **Closed Card Sorting:** Users sort items into predefined categories. Validates whether the proposed structure matches user mental models.
- **Tree Testing:** Present a text-only navigation hierarchy. Ask users to find specific items (e.g., "Where would you find billing history?"). Measures label and hierarchy effectiveness without visual bias.

## Questions

- How many levels deep is the deepest content, and can the user reach any item within 3 actions? (e.g., primary nav → section → item, search → result, shortcut → destination)
- Does the labeling match the vocabulary the user uses, not the system's internal terminology? (e.g., "Projects" vs "Workspaces", "Settings" vs "Configuration", "Help" vs "Documentation")
- At any point in the interface, can the user answer: where am I, how did I get here, and where can I go? (e.g., breadcrumbs, active nav states, contextual back links, page titles)
- What are the 3–5 most frequent destinations, and do they have the shortest access paths? (e.g., home, primary workspace, recent items, search, settings)
- Has the proposed structure been validated with users via card sorting or tree testing, or is it based solely on internal assumptions?
